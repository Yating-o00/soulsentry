# 通用 Harness M1 与 M2 开发计划

从 PR #6 已合入的排程流程与独立的十道通用评测题起步。M1 在真实排程入口验证能力契约。M2 让模型在同一个有预算的循环内动态选择模拟读工具。现有聊天和确认路由承载 M1，M2 通过直接运行 Harness 的评测入口试跑。

## M1 固定基线并接入排程适配器

1. 在当前提交上复跑离线排程回归，保留已提交的十道原始真实模型场景和十道通用题。真实模型同条件对照由既有脚本执行，报告区分离线回归和真实试次。
2. 提供最小 `Capability` 契约。每项能力声明名称、副作用、参数和执行逻辑。模型可见的能力另提供参数描述。调用者身份经服务端上下文传入。
3. 让助手排程的提案校验和已认证确认走排程适配器。提案仍由现有存储承载，确认继续走原事务，在事务里重查归属与空档。复用既有出稿、一次修复及幂等键。保持旧版客户端确认的请求和响应兼容。
4. 保留排程的运行 ID、阶段、终态、耗时和失败码。对照验证提案阶段零任务写入、非法账号无法确认、冲突时拒绝落库、重复确认只写一次。指定星期和多周可用性继续由排程能力处理，已有失败作为后续排程回归。

## M2 动态选择、澄清和完成

1. 接入单次只读运行。模型可以选择 `call`、`ask` 或 `finish`。Harness 校验能力注册、参数、权限、预算和完成证据，执行已注册的读取并把结构化观察交回模型。`ask` 返回问题并结束当前运行。
2. 用两个受账号限制的模拟读取能力验证复用。一个查询记录，另一个查询集合。评测场景包含同名诱饵、跨账号数据、先查记录再查所属集合，以及只有软偏好时直接完成。
3. 复用现有模型调用层提供结构化决策。用注入的 provider 在离线环境检验从提示词、工具调用到最终评分的完整路径。另测未知工具、参数错误、权限拒绝、预算耗尽、无进展重复调用和缺少证据的完成。
4. M2 的验收包括通用题 1 和 3 实际经过新循环，以及独立单次澄清测试。用户回复后续接、版本化写入和恢复由 M3 完成。Always-on 仍是独立调度模块。

## 并行开发和合入

- 排程适配器和真实路由为第一条开发线。
- 通用只读循环及其边界测试为第二条开发线。
- 模拟能力、评测接线及端到端用例为第三条开发线。
- 主线维护共用能力契约和模型决策适配器，逐项整合，再复跑 Harness 与后端回归。
