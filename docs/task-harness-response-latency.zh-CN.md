# 任务 · 建立 Harness 服务端响应耗时基线

## 目标

让管理员能用单轮时间轴定位一条请求慢在哪一步，再用分组统计判断这一步是否经常慢。这个任务给当前流程加计时和看板，后续用同一口径评估对话路由改动。计时单位及其理由见[决策记录](adr/0001-measure-server-latency-per-assistant-request.md)。

## 已确认的设计

- 主指标为[单轮服务端响应耗时](../GLOSSARY.md)。针对已纳入的请求，在 Express 解析请求体和鉴权之前打起点，在 HTTP `finish` 时记录总耗时。提前断开的请求标记为中断。用户补答和确认各自计时，Always-on 后台运行另有自己的计时边界。
- 首版覆盖 `POST /api/companion/messages` 和 `POST /api/companion/harness`。主助理的纯回填 `assistant_echo` 不计入用户消息。通用任务的初始请求、补答和确认分别标记。`/api/chat` 和主助理旧版排程确认接口列为后续接入。
- 请求入口和执行路径分别记录。例如，主助理里的普通聊天、排程追问和排程出稿都来自同一入口。是否进入出稿、校验或修复，按每轮实际执行情况打点。
- 请求开始时记录日期时间以供筛选。各阶段用同一个单调时钟记录开始偏移和耗时。打点汇集在请求内，响应结束后异步保存一条轨迹。轨迹只保留请求标识、已定义的阶段与结果、耗时及模型调用计数等分析字段。
- 轨迹单独存入现有 SQLite，保留最近 30 天并自动清理到期记录。管理员默认看最近 7 天，可在保留范围内筛选和回查明细。

## 与 AI 运行监控协作

耗时轨迹复用现有 AI 请求 ID 和供应商尝试的起止事件。耗时看板记录整个助理请求的阶段分布，包括接入、历史、记忆、校验和落库。AI 运行监控可用同一请求 ID 追查发布版本、具体模型、重试和错误码。耗时看板读取业务 SQLite 中单独的轨迹表，AI 运行监控使用从 journal 建立的独立索引。启动耗时看板只需要业务库 schema，AI 运行监控的采集和告警按各自配置运行。

## 统计口径

- 时间轴保留每次执行的区间。阶段统计以请求为样本，同一轮内合并同一阶段的重叠区间，再累计合并后的时长。两次各 400 毫秒、重叠 200 毫秒的记忆查询，贡献一个 600 毫秒的样本。
- 阶段 P50/P95 使用筛选范围内实际执行过该阶段的请求，显示参与计算的轮数。总耗时 P50/P95 使用每轮请求的起止时间直接计算。
- 分位数按样本从小到大排序后取向上取整的百分位名次。趋势沿用管理看板的北京时间分日。
- 默认总耗时和阶段分位数覆盖进入对话处理并写完响应的请求，包括正常回复、澄清、提案、确认结果、回退和返回超时提示的请求。业务结果由处理路径记录，可独立于 HTTP 状态码筛选。
- 提前断开的请求单列计数、中断率和断开前耗时。中断率的分母是同一观察范围内进入对话处理的全部请求。
- 模型请求次数按发给供应商的尝试计数，包含重试和记忆向量请求。总数包含中断前已经发起的调用。各阶段的模型请求数使用该阶段的已响应样本，供应商阶段展示这些请求的总数。

## 交付内容

1. 在真实请求链上采集阶段时间。首版关注接入、历史与记忆、动作提取、对话模型、规划模型或通用任务决策、能力执行、校验与修复、回复或任务状态保存。一个阶段重复执行时，保留每次的时间区间。
2. 在现有管理员统计页加入一个耗时视图，可按日期、入口、执行路径与结果筛选。总耗时趋势显示每日 P50/P95 和样本数，阶段统计显示各阶段的 P50/P95、样本数和模型调用次数。选中一轮可查看其时间轴，定位并行、修复、超时或回退发生的位置。
3. 用可控时间的测试核对轨迹和汇总，再用现有 Harness HTTP 评测验证实际打点。覆盖普通聊天、排程出稿或修复、通用能力调用和确认，以及超时、断开和错误回退。

## 验收

- 普通聊天的轨迹显示对话模型调用。经过排程出稿的轨迹能分别看到对话模型、规划模型和校验，实际发生修复时能看到追加调用。
- 通用任务的补答和确认有独立轨迹，确认等待期间的用户用时不计入任一请求。业务回退可单独筛出，即使 HTTP 返回 200。
- 服务端总耗时来自请求起止时刻。看板能从同一筛选范围打开原始单轮轨迹。并行区间保留重叠关系。
- 使用一轮正常回复、一轮 HTTP 200 回退和一轮中断验证分组。默认响应分位数的样本数是 2，中断率是 1/3。
- 统计数据仅管理员可读，轨迹中没有消息、提示词、模型输出或工具返回正文。统计写入异常不改变原请求的响应。
- 看板默认查询最近 7 天，30 天保留范围内可以查看单轮明细。清理测试覆盖过期与未过期两类轨迹。
